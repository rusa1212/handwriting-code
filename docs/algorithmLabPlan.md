# 알고리즘 실험실 작업 계획

> 목표: 길찾기 API가 준 완성 경로 대신, **도로망 그래프 위에서 직접 구현한 Dijkstra / A\*** 로 경로를 찾고
> **탐색 과정을 지도에 애니메이션으로 보여준다.** (`mapping.md` LEVEL 4, `webpagePlan.md` 8장 6번)

---

## 진행 현황

| 단계 | 내용 | 구분 | 상태 |
|---|---|---|---|
| 1 | OSM 도로망을 받아 그래프로 변환 (`be/graph.py`) | 필수 | ✅ 완료 |
| 2 | BFS → DFS → Dijkstra → A\* 직접 구현 + 터미널 검증 (`be/search.py`) | 필수 | ✅ 완료 |
| 3 | 백엔드 `POST /api/search` | 필수 | ✅ 완료 |
| 4 | 실험실 화면: 출발/도착 선택 → 알고리즘 선택 → 실행 → 경로 표시 | 필수 | ✅ 완료 |
| 5 | `visited_order` 탐색 애니메이션 | 필수 | ✅ 완료 |
| 6 | Dijkstra vs A\* 비교: 두 지도 나란히 같은 속도로 재생 + 비교 표 (방문 노드 수, 비용, 실행 시간) | 필수 | ⬜ |

6단계까지 끝나면 "방문한 노드가 퍼져나가는 모습이 보이고, A\*가 더 적게 탐색하는 것을 확인"할 수 있다.
그다음 LEVEL 5에서 이 알고리즘을 경로 추천 탭에 통합한다.

현재 1~5단계(백엔드 + 실험실 화면 + 탐색 애니메이션)는 완료됐고, 실험실에서 출발/도착을 찍고 알고리즘을 실행하면 방문 노드가 탐색 순서대로 퍼진 뒤 경로가 그려진다. 6단계(비교) 진행 중.

## 데이터 출처 (중요한 함정)

카카오 길찾기 API는 **완성된 경로**만 돌려주므로 Dijkstra를 돌릴 수 없다. 교차로·도로로 된 **도로망 원본**이 필요하다.

| 용도 | 데이터 출처 |
|---|---|
| 경로 추천 탭 (LEVEL 1~3) | 카카오 길찾기 API |
| 알고리즘 실험실 (LEVEL 4~5) | OpenStreetMap 도로 데이터 (광주 전남대 주변) |
| 지도 표시 | 카카오맵 JS SDK |

그래프 표현:

```text
교차로     = Node  (id, lat, lng)
도로       = Edge  (from, to, 거리 m, 예상 시간 s)
거리/시간  = Weight
```

- 전국을 받으면 너무 크므로 **광주 전남대 주변 2km × 2km만** 받는다. 광주 전체(약 500km²)도 노드가 수십만 개가 되어 지도 점 표시·애니메이션이 감당하지 못한다.
- OSM 데이터는 Overpass API를 `httpx`로 호출해 한 번 받아 JSON으로 저장해 두고, 서버는 그 파일을 읽는다. (`osmnx`는 `geopandas` 등 큰 패키지가 따라와서 쓰지 않는다)
- 받아온 그래프는 일방통행(`oneway`)을 반영해 **방향 그래프**로 두는 것을 기본으로 한다.

## API 약속

| 엔드포인트 | 요청 | 응답 | 상태 |
|---|---|---|---|
| `POST /api/search` | `{ start, end, algorithm, weights }` | `{ path, visited_order, cost, elapsed_ms }` | ✅ |

- `start`, `end`: 좌표 `{ lat, lng }` → 서버에서 **가장 가까운 노드**로 맞춘다.
- `algorithm`: `"bfs" | "dfs" | "dijkstra" | "astar"`
- `path`: `[[lat, lng], ...]` — 기존 `MapView`의 `routes[].path` 형식과 같게 맞춘다.
- `visited_order`: 방문한(확정한) 노드 좌표를 순서대로. 애니메이션에 쓴다.
- `weights`: LEVEL 5에서 사용자 선호도를 반영할 때 쓴다. LEVEL 4에서는 거리만 써도 된다.

## 1단계 ✅ 그래프 구성 (`be/graph.py`)

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 1-1 | `Graph` 자료구조 + A~G 예제 그래프 (`python graph.py`로 확인) | ✅ 완료 |
| 1-2 | 하버사인 거리 + 좌표 → 가장 가까운 노드 찾기 | ✅ 완료 |
| 1-3 | OSM에서 전남대 주변 도로망을 받아 JSON으로 저장 (`python fetch_osm.py`) | ✅ 완료 |
| 1-4 | JSON → `Graph` 읽기, 노드/간선 수 확인 (`load_osm_graph()`) | ✅ 완료 |

- 인접 리스트(딕셔너리)로 표현: `adj = { node_id: [(neighbor_id, weight), ...] }`
- 노드 좌표 표: `coords = { node_id: (lat, lng) }`
- `add_edge(u, v, weight, oneway=False)`: 일방통행이 아니면 반대 방향도 같이 넣는다.
- 예제 그래프의 가중치는 직선거리보다 작지 않게 정했다 (A\* 휴리스틱이 최단 경로를 보장하는지 검증할 때 필요). `python graph.py`가 간선마다 이를 확인해 출력한다.
- `haversine(lat1, lng1, lat2, lng2)`: 두 좌표의 직선거리(m). A\* 휴리스틱으로도 쓴다.
- `Graph.nearest_node(lat, lng)` → `(node_id, 거리 m)`: 전체 노드를 비교한다 (수천 개는 충분히 빠름). 너무 먼지(그래프 영역 밖)는 API 쪽에서 거리로 판단한다.

### 1-3 OSM 내려받기 (`be/fetch_osm.py` → `be/data/gwangju_roads.json`)

- Overpass API(무료, 키 없음)로 **전남대 용봉캠퍼스 (35.1769, 126.9069) 중심 2km × 2km** 영역의 자동차 도로만 받는다.
  - 포함: `motorway`, `trunk`, `primary`, `secondary`, `tertiary`, `unclassified`, `residential`, `*_link`, `living_street`
  - 제외: 인도, 자전거길, 계단, 주차장 통로(`service`) 등
  - 예외: **전남대 캠퍼스 경계 안의 `service`(차량 통행로)는 받는다** (아래 "캠퍼스 안 길 추가" 참고)
- 저장 형식: `{ attribution, bbox, nodes: { id: [lat, lng] }, ways: [{ id, nodes: [node_id...], tags }] }`
  - 태그는 `highway`, `oneway`, `maxspeed`, `name`, `junction`만 남긴다.
- 영역 밖까지 이어지는 도로는 잘리지 않고 끝까지 들어온다.
- 받은 결과 (2026-10-11): 도로 295개, 점 1,409개, 105KB, 일방통행 46개
- 캠퍼스 안 길은 대부분 `service`라 받지 않는다 → 캠퍼스가 빈 공간이 되고, 캠퍼스 중심을 찍으면 약 300m 떨어진 바깥 도로에 맞춰진다 (500m 규칙 안).

**캠퍼스 안 길 추가 (2026-10-14)**

- 캠퍼스 경계 = OSM `amenity=university`, `name=전남대학교`인 way `105125653` (`CAMPUS_WAY_ID`). Overpass에서 `map_to_area`로 영역으로 바꿔 그 안의 `highway=service`만 더 받는다.
- 캠퍼스 안 길 952개 중: `footway` 638, `service` 214 (그중 `parking_aisle` 5), `path` 39, `steps` 37, `pedestrian` 14 등.
  - **차량 통행로(`service`)만 넣고 주차장 통로(`parking_aisle`)와 보행로는 뺀다.** 자동차 도로 그래프라서 경로가 인도·계단으로 지름길을 내면 안 되고, LEVEL 5에서 시간 가중치를 붙이기도 쉽다.
  - 영역 전체의 `service`를 받지 않는 이유: 건물 진입로·주차장 통로까지 잔뜩 들어와 노드가 크게 늘어난다.
  - 캠퍼스 길에는 `access` 태그가 없어 차량 통행 제한은 반영하지 않는다 (실제로 정문·후문으로 통과할 수 있다고 본다).
- 저장할 태그에 `service`를 추가했다 (`KEEP_TAGS`).
- 받은 결과: 도로 295 → **504개** (`service` 209개 추가), 점 1,409 → **2,758개**, 193KB, 일방통행 68개.
- 서버는 이 파일만 읽는다. 영역을 바꿀 때만 다시 실행한다.

주의할 점:

- 기본 User-Agent(`python-httpx`)는 **406으로 거절**되므로 User-Agent를 직접 넣는다.
- 공용 서버가 바쁘면 **504("server is probably too busy")** 가 자주 난다. 잠시 기다렸다 서버를 바꿔 가며 다시 시도하게 했다 (0 → 5 → 15 → 30 → 60초).
- 화면에 표시할 때 "© OpenStreetMap contributors" 출처를 적어야 한다 (ODbL).

### 1-4 JSON → 그래프 (`load_osm_graph()`)

- 도로(way)의 이웃한 두 점마다 간선을 만든다. 가중치 = 두 점 사이 하버사인 거리(m).
- 도로가 꺾이는 점도 노드가 된다 → 노드 수가 교차로 수보다 많다 (애니메이션이 촘촘해진다).
- 통행 방향 (`_direction`):
  - `oneway=yes/true/1` → 점 순서대로만, `oneway=-1` → 반대로만, `oneway=no` → 양방향
  - 태그가 없어도 `highway=motorway`, `junction=roundabout`은 일방통행 (OSM 규칙)
- `python graph.py` 결과 (2026-10-11 데이터, 가장 큰 덩어리만 남긴 뒤):
  - 간선 길이: 최소 0.7m, 평균 36.4m, 최대 269.6m
  - 전남대 캠퍼스 중심에서 가장 가까운 노드까지 297.6m (캠퍼스 안 길이 없어서)
- 캠퍼스 길을 추가한 뒤 (2026-10-14 데이터): 원본 노드 2,758개 → 가장 큰 덩어리 **2,609개**, 방향 간선 5,315개, 모두 서로 오갈 수 있음 `True`
  - 간선 길이: 최소 0.4m, 평균 25.3m, 최대 269.6m
  - 캠퍼스 중심에서 가장 가까운 노드까지 **13.9m**
  - 덩어리에서 빠진 노드가 124 → 149개로 늘었다: 캠퍼스 안에서 다른 길과 이어지지 않은 `service` 조각

**연결되지 않은 부분 → 가장 큰 덩어리만 남긴다 (`keep_largest=True`, 기본값)**

원본 그래프에서는 전남대 근처 노드에서 갈 수 있는 노드가 1,302 / 1,409개였다. 나머지는 대부분 **호남고속도로**(본선·연결로)와 서암대로 일부다. 고속도로는 영역 안에서 일반 도로와 양방향으로 이어지지 않아 영역 밖으로 나가야만 이어진다.
지도 클릭이 이런 노드에 붙으면 "경로 없음"이 나오므로 그래프를 만들 때 뺀다.

- 일방통행이 있으므로 **서로 오갈 수 있는** 노드끼리 묶는다 (강한 연결 요소). 한쪽으로만 갈 수 있는 노드를 남기면 출발/도착을 바꿨을 때 경로가 없을 수 있다.
- `Graph.largest_component()`: 노드 u의 덩어리 = u에서 갈 수 있는 노드 ∩ u로 올 수 있는 노드. 아직 덩어리가 정해지지 않은 노드마다 반복해 가장 큰 것을 고른다.
- `Graph.keep_only(nodes)`: 그 덩어리만 남기고 바깥으로 이어지는 간선도 지운다.

| | 노드 | 방향 간선 | 나가는 간선 없는 노드 |
|---|---|---|---|
| 원본 | 1,409 | 2,807 | 6 |
| 가장 큰 덩어리만 | 1,285 | 2,680 | 0 |

- 빠진 노드 124개: 호남고속도로 본선 85개·연결로 8개, 서암대로 19개, 운용로95번길 8개 등 (영역 경계에서 한 방향만 남은 구간 포함)
- `python graph.py`가 남은 노드끼리 모두 오갈 수 있는지 확인한다 → `True`

## 2단계 ✅ 탐색 알고리즘 (`be/search.py`)

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 2-0 | 예제 그래프 가중치 수정 (B─E 300m → 350m) | ✅ 완료 |
| 2-1 | 공통 틀: `(path, visited_order, cost)` 결과 형태, `parent`로 경로 복원, `python search.py` 출력 뼈대 | ✅ 완료 |
| 2-2 | BFS (간선 수 최소) | ✅ 완료 |
| 2-3 | DFS (스택, 최단 보장 없음) | ✅ 완료 |
| 2-4 | Dijkstra (`heapq`, 확정 순서 = `visited_order`) | ✅ 완료 |
| 2-5 | A\* (휴리스틱 = 하버사인) | ✅ 완료 |
| 2-6 | 광주(전남대) OSM 그래프로 Dijkstra vs A\* 검증 + 예외 상황 | ✅ 완료 |

### 2-0 예제 그래프 수정

- 원래 B─E가 300m라 B → G 최단 경로가 B-E-G(420m)였다. B-A-D-E-G(440m)보다 짧아서 BFS와 Dijkstra가 같은 경로를 냈다.
- B─E를 350m로 올렸다 → Dijkstra: B-A-D-E-G **440m**, BFS: B-E-G **470m** (간선 2개). 두 알고리즘의 차이가 드러난다.

### 2-1 공통 틀

- `SearchResult(path, visited_order, cost)`: `NamedTuple`이라 `path, visited, cost = result`로 풀어 쓸 수도 있다.
  - `path`, `visited_order`는 **노드 id**. 좌표로 바꾸는 것은 3단계 API에서 한다.
  - 경로가 없으면 `path = []`, `cost = inf`. 출발 = 도착이면 `path = [start]`, `cost = 0`.
- `reconstruct_path(parent, start, end)`: 탐색은 `parent[start] = None`으로 시작하고, 노드에 처음 도착할 때 거쳐 온 노드를 적는다. 도착 노드에서 거꾸로 따라가 뒤집는다.
- `path_cost(graph, path)`: BFS/DFS는 가중치를 보지 않으므로 경로를 찾은 뒤 비용을 따로 계산한다.
- `make_result(...)`: 위 둘을 묶어 결과를 만든다. 알고리즘마다 마지막 줄에서 이것만 부르면 된다.
- `ALGORITHMS = { "bfs": bfs, ... }`: 2-2부터 채운다. 3단계 API가 `algorithm` 문자열로 함수를 고를 때도 쓴다.
- `python search.py`: Windows 터미널에서 한글이 깨지지 않게 출력을 UTF-8로 바꾼다.

### 2-2 BFS (`bfs()`)

- `deque` 큐. 노드를 **처음 발견할 때** `parent`를 정하고 큐에 넣는다 → 간선 수가 가장 적은 경로.
- `visited_order` = 큐에서 꺼낸 순서. 도착 노드를 꺼내면 멈춘다 (Dijkstra의 "확정"과 같은 시점으로 맞춤).
- 가중치를 보지 않으므로 비용은 `path_cost()`로 따로 계산한다.
- `python search.py` 결과 (예제 그래프, 기대값은 `EXPECTED`, 떨어진 노드 H를 붙여 "경로 없음"도 확인):

| 출발 → 도착 | 경로 | 비용 | 방문 순서 |
|---|---|---|---|
| B → G | B-E-G | 470m | B A C E D F G |
| A → F | A-B-C-F | 370m (A-D-E-F 320m와 간선 수 같음, 먼저 발견한 쪽) | A B D C E F |
| G → G | G | 0m | G |
| B → H | 없음 | inf | B A C E D F G (전부 방문) |

### 2-3 DFS (`dfs()`)

- 재귀 대신 **스택**: OSM 그래프는 노드가 1,285개라 재귀 깊이 제한(기본 1000)에 걸릴 수 있다.
- 스택에 `(노드, 거쳐 온 노드)`를 넣고, **꺼낼 때** 방문 처리와 `parent`를 정한다. 같은 노드가 여러 번 들어갈 수 있으므로 이미 방문한 노드는 건너뛴다.
  - BFS처럼 넣을 때 `parent`를 정하면 "먼저 발견한 쪽"이 경로가 되어 진짜 DFS 순서와 달라진다.
- 이웃을 거꾸로 넣어 첫 번째 이웃을 먼저 방문한다 (재귀 DFS와 같은 순서).
- `python search.py` 결과 (예제 그래프):

| 출발 → 도착 | 경로 | 비용 | 방문 순서 |
|---|---|---|---|
| B → G | B-A-D-E-G | 440m (A로 먼저 들어간 덕에 우연히 최단) | B A D E F C G |
| G → A | G-E-B-A | 570m (최단은 G-E-D-A 340m) | G E B A |

- 광주 OSM 그래프에서 같은 출발/도착(3-2의 영역 남서쪽 → 북동쪽)으로 돌려 본 결과: BFS 3,570m (노드 75개) vs DFS **9,028m** (노드 290개). 도로망을 크게 휘젓고 다니는 경로가 나온다.

### 2-4 Dijkstra (`dijkstra()`)

- `heapq`에 `(지금까지 거리, 노드)`를 넣고, 거리가 가장 짧은 노드를 꺼내 **확정**한다. 확정 순서 = `visited_order`, 도착 노드를 확정하면 멈춘다.
- 더 짧은 거리를 찾으면 새 항목을 넣기만 하고 옛 항목은 지우지 않는다. 꺼냈을 때 이미 확정된 노드면 버린다 (heapq에는 "값 줄이기"가 없어서 쓰는 흔한 방법).
- `python search.py` 결과 (예제 그래프):

| 출발 → 도착 | 경로 | 비용 | 방문 순서 | 비교 |
|---|---|---|---|---|
| B → G | B-A-D-E-G | 440m | B A C D F E G | BFS는 B-E-G 470m |
| G → A | G-E-D-A | 340m | G E D F A | DFS는 G-E-B-A 570m |
| A → F | A-D-E-F | 320m | A B D E C F | BFS는 A-B-C-F 370m |

- 광주 OSM 그래프 무작위 200쌍: Dijkstra 비용이 BFS·DFS보다 긴 경우 **0건**, 평균 실행 시간 약 0.6ms.
- 2-3과 같은 쌍: Dijkstra 3,010m (BFS 3,570m, DFS 9,028m). 방문 노드는 1,200개로 BFS(912개)보다 많다 → 2-5 A\*로 줄일 대상.

### 2-5 A\* (`astar()`)

- 다익스트라와 구조는 같고 우선순위만 다르다: `f = g(출발 → 노드 거리) + h(노드 → 도착 직선거리)`.
- 간선마다 "도로 거리 ≥ 직선거리"이므로 h가 남은 거리를 부풀리지 않고, 한 번 확정한 노드를 다시 열 필요도 없다 → 다익스트라와 같은 `done` 집합 방식 그대로 최단 경로.
  - 예제 그래프는 1-1에서 가중치를 직선거리 이상으로 정했고, OSM 그래프는 가중치가 곧 하버사인 거리라 이 조건을 만족한다.
- `python search.py` 결과 (예제 그래프): 경로·비용은 다익스트라와 모두 같다.

| 출발 → 도착 | 비용 | 다익스트라 방문 | A\* 방문 |
|---|---|---|---|
| B → G | 440m | 7개 | 7개 |
| G → A | 340m | 5개 | **4개** (F를 건너뜀) |
| A → F | 320m | 6개 | **5개** (C를 건너뜀) |

- 광주 OSM 그래프 무작위 200쌍:
  - 비용이 다익스트라와 다른 경우 **0건**, A\*가 더 많이 방문한 경우 **0건**
  - 평균 방문 노드: 다익스트라 653개 → A\* **226개 (35%)**
  - 평균 실행 시간: 다익스트라 0.61ms, A\* 0.57ms (방문은 1/3이지만 매번 하버사인을 계산하므로 시간 차이는 작다)
  - 2-3과 같은 쌍: 둘 다 3,010m, 방문 1,200개 → **580개**

### 2-6 광주(전남대) OSM 그래프 검증 (`_check_osm()`)

- `python search.py`의 마지막 부분. 무작위 200쌍(seed 고정 → 매번 같은 쌍)으로 네 알고리즘을 돌려 확인한다:
  - 모든 쌍에서 경로가 있고 출발/도착이 맞는지
  - A\* 비용 = 다익스트라 비용, A\* 방문 수 ≤ 다익스트라 방문 수
  - BFS/DFS 비용이 다익스트라보다 짧지 않은지
- 결과 (2026-10-11, 전체 실행 1초 미만): **문제 0건**

| 알고리즘 | 평균 비용 | 평균 방문 | 평균 시간 |
|---|---|---|---|
| BFS | 2,060m | 642개 | 0.28ms |
| DFS | 6,223m | 667개 | 0.43ms |
| Dijkstra | 1,752m | 653개 | 0.61ms |
| A\* | 1,752m | **226개 (35%)** | 0.57ms |

- 예외 상황:
  - 출발 = 도착: 네 알고리즘 모두 경로 1개 노드, 비용 0
  - 경로 없음: OSM 그래프는 가장 큰 덩어리만 남겨 생기지 않는다. 예제 그래프에 떨어진 노드 H를 붙여 확인했다 (→ `[]`, `inf`)
  - 영역 밖 클릭: 전남대 캠퍼스 중심은 가장 가까운 노드까지 298m, 북쪽 3.7km 지점은 2,128m → 3단계 API에서 이 거리로 오류를 낸다 (예: 500m 이상)

- 순서: BFS → DFS → Dijkstra → A\*
- 라이브러리의 최단경로 함수를 쓰지 않고 **핵심 부분을 직접 구현**한다. (우선순위 큐는 `heapq` 사용)
- A\* 휴리스틱: 두 좌표 사이의 직선 거리(하버사인). 실제 도로 거리보다 크지 않으므로 최단 경로를 보장한다.
- 모든 알고리즘이 `(path, visited_order, cost)`를 같은 형태로 돌려주게 한다.
- **웹에 붙이기 전에 터미널에서 작은 그래프(A~G 노드)로 먼저 검증한다.** 웹에서 디버깅하면 원인이 화면 쪽인지 알고리즘 쪽인지 구분하기 어렵다.

```text
A ─ B ─ C
│   │   │
D ─ E ─ F
    │
    G
```

## 3단계 ✅ 백엔드 `/api/search`

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 3-1 | 요청/응답 Pydantic 모델 (`be/schemas.py`) | ✅ 완료 |
| 3-2 | 좌표 → 노드 → 탐색 → 좌표 변환 함수 (`be/lab.py`, 터미널 확인) | ✅ 완료 |
| 3-3 | `POST /api/search` 연결 + 오류 응답, `/docs`에서 확인 (`be/main.py`) | ✅ 완료 |

- `/docs`에서 먼저 응답을 확인한 뒤 프론트에 붙인다.

### 3-1 요청/응답 모델 (`schemas.py`)

- `LatLng`: `{ lat, lng }` (위도 ±90, 경도 ±180 범위 검사). 기존 `Place`는 `name`이 필수라 따로 만들었다.
- `SearchRequest`: `start`, `end`(`LatLng`), `algorithm`(`Literal["bfs", "dfs", "dijkstra", "astar"]`), `weights`(`Weights | None`, LEVEL 4에서는 쓰지 않음)
  - `algorithm`을 `Literal`로 두면 잘못된 값은 FastAPI가 알아서 422로 거절한다.
- `SearchResponse`: `path`(`[[lat, lng], ...]`, 기존 `Route.path`와 같은 형식), `visited_order`(`[[lat, lng], ...]`), `cost`, `elapsed_ms`
  - `cost`는 `float | None`: 경로가 없을 때 `inf`는 **JSON으로 보낼 수 없으므로** `None`(null)으로 바꾼다.
  - `elapsed_ms`: 6단계 비교에 쓸 탐색 시간. 탐색 함수만 잰다 (좌표 변환·네트워크 제외).

### 3-2 탐색 실행 함수 (`lab.py`)

- 그래프는 서버가 처음 쓸 때 **한 번만** 읽어 둔다 (`functools.cache`로 `load_osm_graph()` 감싸기). 요청마다 JSON을 읽지 않는다.
- `run_search(start, end, algorithm) -> SearchResponse` 흐름:
  1. `Graph.nearest_node()`로 출발/도착 좌표를 노드에 맞춘다. 둘 중 하나라도 **500m 이상** 떨어지면 `OutOfAreaError`
  2. `ALGORITHMS[algorithm]`로 탐색, `time.perf_counter()`로 시간 측정
  3. `path`, `visited_order`의 노드 id → `graph.coords` 좌표로 바꾼다
- 출발/도착 노드가 같으면 2단계 규칙 그대로 `path = [그 노드]`, `cost = 0`.
- `python lab.py`: 영역 남서쪽 → 북동쪽, 영역 밖 좌표(전남대 북쪽 3.7km)를 넣어 결과와 오류를 터미널에서 확인한다.
  - 캠퍼스 중심은 바깥 도로까지 약 300m 떨어진 막다른 노드에 맞춰지므로 예시로 쓰지 않고, 도로 위 두 점을 쓴다.
- `OutOfAreaError(label, distance)`: 메시지에 출발지/도착지 중 어느 쪽인지와 거리를 담는다. 3-3에서 그대로 400 응답으로 보낸다.
- `python lab.py` 결과 (영역 남서쪽 (35.1735, 126.9000) → 북동쪽 (35.1820, 126.9150), 직선거리 약 1.6km):

| 알고리즘 | 비용 | 경로 점 | 방문 | 시간 |
|---|---|---|---|---|
| BFS | 3,570m | 75 | 912개 | 0.44ms |
| DFS | 9,028m | 290 | 610개 | 0.41ms |
| Dijkstra | 3,010m | 134 | 1,200개 | 1.10ms |
| A\* | 3,010m | 134 | **580개** | 1.20ms |

- 출발 = 도착: 경로 1점, 비용 0. 영역 밖(북쪽 3.7km): 출발/도착 모두 "가장 가까운 도로까지 2,128m" 오류
- 한 번씩 잰 시간이라 오차가 크다 (이 쌍에서는 A\*가 Dijkstra보다 조금 느리게 나왔다). 평균은 2-6의 무작위 200쌍 결과를 본다.
- 그래프 캐시: 두 번째 `get_graph()` 호출은 바로 돌아온다 (JSON을 다시 읽지 않음)

### 3-3 엔드포인트 (`main.py`)

- `POST /api/search` → `run_search()` 호출. 다른 엔드포인트처럼 주석 한 줄을 붙인다.
- 오류 응답:

| 상황 | 응답 |
|---|---|
| 영역 밖 좌표 (`OutOfAreaError`) | 400, "출발지(도착지)가 실험 영역 밖입니다" + 가장 가까운 도로까지 거리 |
| 잘못된 `algorithm` | 422 (Pydantic이 처리) |
| 경로 없음 | 200, `path = []`, `cost = null` (오류가 아니라 결과로 본다) |

- `/docs`에서 네 알고리즘을 같은 출발/도착으로 보내 2-6 결과와 비용이 맞는지, A\*의 `visited_order`가 다익스트라보다 짧은지 확인한다.
- 확인 결과 (2026-10-11, 실행 중인 서버에 `/docs`와 같은 요청):
  - 3-2와 같은 출발/도착: 네 알고리즘 모두 200, 비용·방문 수가 3-2 결과와 같다 (A\* 580개 vs 다익스트라 1,200개)
  - 출발 = 도착: 200, `cost = 0`, 경로 1점
  - 영역 밖: 400, `"도착지가 실험 영역 밖입니다 (가장 가까운 도로까지 2,128m)"`
  - `algorithm = "greedy"`: 422, `weights`를 보내도 200 (아직 쓰지 않음)
  - 경로 없음(200, `cost = null`)은 OSM 그래프가 모두 연결되어 있어 API로는 만들 수 없다. 변환 코드(`inf` → `None`)만 있다.

### 4-2 실험 영역 경계 표시

- 그래프는 전남대 주변 2km만 있으므로 **어디를 클릭해야 하는지** 지도에 보여 준다. 없으면 영역 밖을 찍고 400 오류부터 보게 된다.
- `MapView`에 `rects: [{ south, west, north, east }]` prop을 추가해 `kakao.maps.Rectangle`(옅은 채우기 + 점선 테두리)로 그린다. 다른 탭에는 영향이 없다 (기본값 `[]`).

### 4-3 출발/도착 고르기

- 실험실에서는 항상 지점 선택 모드다: `onMapClick`을 늘 넘긴다 (십자 커서도 그대로 나온다).
- 클릭 순서: 출발 → 도착 → 다시 클릭하면 새 출발 (도착과 결과는 지운다). 사이드바에 "출발지를 클릭하세요" / "도착지를 클릭하세요" 안내.
- 주소 변환(`reverseGeocode`)은 하지 않는다. 핀 라벨은 "출발", "도착"만. 좌표만 있으면 되고 카카오 API 호출을 줄인다.
- "초기화" 버튼: 출발/도착/결과를 모두 지운다.
- 핀은 클릭한 지점에 찍히고, 경로는 서버가 맞춘 **가장 가까운 노드**에서 시작하므로 핀과 경로 끝이 조금 떨어질 수 있다 (최대 500m). 이상한 것이 아니다.

### 4-4 알고리즘 선택 + 실행

- 사이드바: 알고리즘 라디오 버튼 4개 (BFS / DFS / Dijkstra / A\*, 기본 A\*) + "실행" 버튼 (출발·도착이 모두 있을 때만 활성).
- 실행하면 `searchGraph()` → 결과 `path`를 `routes=[{ id: 'search', path }]`, `selectedId='search'`로 넘겨 강조 색으로 그린다. `MapView`가 경로에 맞춰 범위를 조정한다.
- 결과 요약: 알고리즘 이름, 경로 거리(`formatDistance()` 재사용), 방문 노드 수, 탐색 시간(ms).
  - `cost = null`이면 "경로를 찾을 수 없습니다".
- 오류(영역 밖 400 등)는 사이드바에 메시지로 보여준다.
- 실행 중에 출발/도착을 바꾸거나 다시 실행하면 이전 응답은 버린다 (`searchIdRef`, 경로 추천 탭과 같은 방식).
- 알고리즘만 바꾸면 결과는 그대로 두고, 다시 "실행"을 눌러야 바뀐다 (6단계 비교 화면에서 나란히 보여줄 예정).
- 확인: `npm run dev`로 같은 출발/도착에서 네 알고리즘을 실행해 3-2 결과와 비용·방문 수가 맞는지, DFS가 크게 돌아가는 경로를 그리는지 본다.

- 상태(몇 개까지 보여줄지)는 페이지가 갖고 `MapView`는 그리기만 한다 (4단계와 같은 방식).
- 방문 노드는 많아야 그래프 전체 노드 수다 (3-2 결과: Dijkstra 1,200개, BFS 912개 / 그래프 전체 1,285개). `Marker`는 무거우므로 쓰지 않는다.

### 5-1 방문 노드 점 그리기 (`MapView`의 `dots`)

- `dots: [[lat, lng], ...]` prop (기본값 `[]`). `visited_order`를 그대로 넘긴다.
- `kakao.maps.Circle`(반지름 몇 m, 테두리 없음, 옅은 채우기)로 그린다. 반지름이 미터 단위라 지도를 확대·축소해도 도로와 함께 커지고 작아진다. 크기는 `LAB_LEVEL`에서 보기 좋게 조정한다.
  - 경로 선보다 아래에 그린다 (`zIndex`: 영역 사각형 0 < 점 1 < 경로 2 < 선택한 경로 3). Kakao가 `zIndex`를 CSS로 쓸 수 있어 소수 대신 정수로 두고 기존 경로 값을 하나씩 올렸다.
- `rects`처럼 경로·핀과 **따로 된 effect**에서 그리고, 지도 범위 맞추기(`setBounds`)에는 넣지 않는다.
- 이 세그먼트에서는 결과가 오면 점을 한 번에 전부 찍는다 → 4단계 결과에 탐색 범위가 보이는 것까지 확인. Dijkstra(1,200개)로 지도 이동·확대가 버벅이지 않는지 본다.

### 5-2 앞에서부터 n개만 보이기 (`dotCount`)

- `dotCount` prop (기본값 `Infinity` = 전부): 앞에서부터 `dotCount`개만 지도에 올린다.
- 프레임마다 점 전체를 지우고 다시 만들면 낭비이므로 나눠서 처리한다:
  - `dots`가 바뀔 때: `Circle`을 전부 **지도에 올리지 않은 채로**(`map` 없이) 만들어 ref에 담아 둔다.
  - `dotCount`가 바뀔 때: 지금 보이는 개수와 비교해 **늘어난 부분만** `setMap(map)`, 줄어든 부분은 `setMap(null)`.
- 확인: 페이지에서 `dotCount`를 고정값(예: 100)으로 넘겨 앞부분만 보이는지 본다.

### 5-3 재생 (`AlgorithmLabPage.jsx`)

- 상태 `shownCount`: 새 결과가 오면 0부터 시작해 `requestAnimationFrame`마다 `STEP`개씩 늘린다. `visited_order.length`에 닿으면 멈춘다.
- `STEP`은 **알고리즘과 상관없이 고정** (예: 프레임당 5개 ≈ 초당 300개 → Dijkstra 1,200개 약 4초, A\* 580개 약 1.9초).
  - 전체 시간을 맞추면 A\*와 Dijkstra가 똑같이 끝나 보인다. 고정 속도여야 "A\*가 빨리 끝난다"가 눈에 보인다 (6단계 비교와 이어짐).
- 재생 중(`shownCount < visited_order.length`)이면 `useEffect`가 다음 프레임 하나를 예약해 `shownCount`를 늘리고, 값이 바뀌면 다시 실행되어 이어진다. cleanup에서 `cancelAnimationFrame` → 다음 경우 자동으로 멈춘다:
  - 출발/도착을 바꾸거나 방향 바꾸기·초기화 (`clearResult()`가 `result`를 지움)
  - 다시 실행 (새 `result`), 다른 탭으로 이동 (언마운트)
- `result`가 없으면 `dots = []`.

### 5-4 끝난 뒤 경로 그리기 + 진행 표시

- `routes`는 **재생이 끝났을 때만** 만든다 (`shownCount === visited_order.length`). 그전에는 점만 퍼져 나간다.
- 경로가 나타나면 `MapView`가 경로에 맞춰 `setBounds`로 확대한다. 탐색 범위(점)가 경로보다 넓으면 점 일부가 화면 밖으로 밀려난다 → 확인해 보고 어색하면 `dots`도 범위에 넣는 옵션을 검토한다.
- 사이드바 결과 패널: 재생 중에는 "탐색 중 · 방문 n / 전체 개" 진행 표시, 끝나면 지금의 결과 요약(거리·경로 노드·방문 노드·탐색 시간).
  - 결과 숫자는 서버 응답 그대로이므로 재생 중에도 보여 줘도 된다. 진행 표시는 그 위에 한 줄 추가하는 정도로 둔다.
- 경로 없음(`cost = null`, `path = []`): 재생은 그대로 하고, 끝나면 "경로를 찾을 수 없습니다".

### 5-5 건너뛰기 / 다시 보기

- "건너뛰기": `shownCount`를 바로 끝까지 → 재생이 멈추고 경로가 그려진다 (예외 상황 표의 "애니메이션이 느림" 대응).
- "다시 보기": 서버를 다시 부르지 않고 `shownCount`를 0으로 되돌려 같은 결과를 다시 재생한다.
  - 진행 상황이 `shownCount` 하나뿐이라 0으로 되돌리기만 하면 재생 effect가 다시 돈다. 건너뛰기도 끝까지 올리기만 하면 된다 (effect 안 지역 변수로 세면 건너뛴 뒤 다음 프레임이 값을 되돌리므로 이렇게 바꿨다).
- 재생 중에는 "건너뛰기", 끝난 뒤에는 "다시 보기"만 보여 준다.

### 5-6 화면 확인

- `npm run dev`, 3-2와 같은 출발/도착(영역 남서쪽 (35.1735, 126.9000) → 북동쪽 (35.1820, 126.9150))에서:
  - Dijkstra: 출발지 둘레로 **원처럼** 퍼진다. A\*: 도착지 쪽으로 **길쭉하게** 뻗고 훨씬 빨리 끝난다.
  - BFS: 간선 수 기준으로 퍼진다. DFS: 한쪽으로 길게 파고들다 돌아온다.
  - 방문 점 개수가 결과 요약의 방문 노드 수와 같은지.
- 예외 상황:
  - 출발 = 도착(같은 노드): 점 1개, 경로 없이 바로 끝난다.
  - 재생 중 지도 클릭 / 방향 바꾸기 / 초기화 / 다시 실행 / 탭 이동: 이전 점이 남거나 재생이 계속되지 않는지.
  - 영역 밖 오류(400): 점·경로 없이 오류 메시지만.

**API로 먼저 확인한 것 (2026-10-11, 화면이 받는 `/api/search` 응답 그대로)**

| 알고리즘 | 비용 | 경로 점 | 방문 | 재생 시간 (프레임당 5개, 60fps) | 방문 노드의 경로 옆 평균 거리 |
|---|---|---|---|---|---|
| BFS | 3,570m | 75 | 912개 | 3.0초 | 583m |
| DFS | 9,028m | 290 | 610개 | 2.0초 | 582m |
| Dijkstra | 3,010m | 134 | 1,200개 | 4.0초 | 590m |
| A\* | 3,010m | 134 | **580개** | **1.9초** | **391m** |

- 네 알고리즘 모두 방문 첫 점 = 경로 시작, 마지막 점 = 경로 끝 (재생이 끝나는 순간 경로 끝이 마지막으로 찍힌다).
- Dijkstra는 영역 노드 1,285개 중 1,200개를 방문한다 → 출발/도착이 영역의 양 끝이라 "원"이 영역 경계에서 잘린다. A\*는 절반 이하이고 경로 옆으로 덜 퍼진다.
- 출발 = 도착: 200, 방문 1개, 경로 1점, 비용 0. 영역 밖: 400 "도착지가 실험 영역 밖입니다 (가장 가까운 도로까지 2,128m)".
- 캠퍼스 중심에서 출발: 핀과 경로 시작이 298m 떨어진다 (캠퍼스 안 길이 없어서).
- 남은 것: 지도에서 실제로 점이 퍼지는 모습, 1,200개 점을 만들 때 버벅임, 재생 중 조작, 경로가 나타날 때와 "다시 보기" 때 지도 범위.

## 6단계 ⬜ Dijkstra vs A\* 비교

- 같은 출발/도착으로 두 알고리즘을 실행해 **방문 노드 수, 경로 비용, 실행 시간**을 나란히 보여준다.
- 두 알고리즘의 경로 비용은 같고, A\*의 방문 노드 수가 더 적어야 한다.
- 숫자뿐 아니라 **탐색이 퍼지는 모습**도 나란히 비교한다: 두 지도를 옆에 두고 하나의 시계로 같은 속도로 재생하면 A\*가 먼저 끝나고 덜 퍼지는 것이 그대로 보인다.
  - 한 지도에 두 색으로 겹치는 방식은 A\* 방문 노드가 Dijkstra와 거의 겹쳐 색이 섞이므로 쓰지 않는다. 나란히 두면 `MapView`를 거의 그대로 두 번 쓸 수 있다.

```text
┌ 사이드바 ┐┌──── Dijkstra ────┐┌────── A* ───────┐
│ 비교 모드 ││   ●●●●●●●●●     ││      ●●●        │
│ [Dij][A*]││  ●●●●출발●●●●   ││     ●출발●●     │
│ ▶ ×1 ×2  ││   ●●●●●●●●●     ││        ●●●도착  │
│ 비교 표   ││ 방문 820/1,200   ││ ✅ 완료 580      │
└──────────┘└──────────────────┘└──────────────────┘
```

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 6-1 | 방문 순서 색 그라데이션 + 방금 찍힌 점 강조 | ⬜ |
| 6-2 | `MapView`에 `fitRoutes` prop: 실험실에서는 경로에 맞춰 지도를 옮기지 않는다 | ⬜ |
| 6-3 | 재생 조작: 일시정지/재개, 속도 ×0.5 / ×1 / ×2 / ×4 | ⬜ |
| 6-4 | 비교 모드 토글 + 알고리즘 두 개 선택 + 두 지도 레이아웃 | ⬜ |
| 6-5 | 공통 시계(`frame`)로 두 지도 동시 재생, 각자 끝나는 순간 경로 그리기 | ⬜ |
| 6-6 | 비교 표 (방문 노드, 경로 거리, 경로 노드, 탐색 시간, 재생 시간) | ⬜ |
| 6-7 | 화면 확인: 점 2,400개 성능, 두 지도 범위, 예외 상황 | ⬜ |

- 6-1~6-3은 비교 모드가 아니어도(알고리즘 하나만 실행해도) 바로 좋아지므로 먼저 한다.
- 시작 전에 5-6 화면 확인 결과를 반영한다: 버벅임이 있으면 6-7 성능 대응을, "다시 보기" 때 범위가 어색하면 6-2를 서두른다.
- 백엔드는 바꾸지 않는다. `/api/search`를 알고리즘마다 한 번씩 부른다.

### 6-1 방문 순서 색 그라데이션

- 지금은 방문 점이 모두 같은 색이라, 재생이 끝나면 어느 쪽으로 먼저 퍼졌는지 알 수 없다.
- `MapView`가 점 `i`의 색을 `i / 전체`로 두 색 사이에서 보간한다 (예: 초기 노랑 `#ffd400` → 후반 빨강 `#e0301e`). 투명도로 차이를 내면 겹친 곳이 탁해지므로 색으로 낸다.
  - Dijkstra는 출발지 둘레에 동심원 띠가, A\*는 도착지 쪽으로 이어지는 띠가 남는다.
- 방금 찍힌 점(예: 최근 `STEP × 6`개 ≈ 0.1초 분량)은 더 크고 진하게 그려 **지금 탐색 중인 경계**가 보이게 한다. 경계를 벗어난 점은 보통 스타일로 되돌린다 (`setOptions`). 재생이 끝나면 모두 보통 스타일.
  - 경계 점만 스타일을 바꾸므로 프레임마다 바뀌는 원은 수십 개뿐이다.
- 색은 `dots`가 바뀔 때 원을 만들면서 한 번만 정한다 (5-2의 "만들어 두기" 그대로).

### 6-2 지도 범위 고정 (`fitRoutes`)

- `MapView`는 경로가 생기면 `setBounds`로 경로에 맞춰 확대한다. 실험실에서는 탐색 범위(점)가 경로보다 넓어서 점 일부가 화면 밖으로 밀려나고, "다시 보기" 때도 확대된 채로 재생된다.
- `fitRoutes` prop(기본값 `true`)을 추가하고, `false`면 `setBounds`를 하지 않는다. 실험실은 `false`를 넘겨 항상 `LAB_CENTER`/`LAB_LEVEL` 화면(실험 영역 전체)을 유지한다.
- 경로 추천 탭은 기본값 그대로라 바뀌지 않는다.
- 비교 모드에서 두 지도의 화면을 똑같이 맞추는 데도 필요하다.

### 6-3 재생 조작 (일시정지 / 속도)

- 상태 `paused`(기본 `false`)와 `speed`(기본 1)를 추가한다.
  - 재생 effect: `if (!playing || paused) return`. 증가량은 `STEP * speed`로 한다.
  - 진행 상황은 지금처럼 숫자 하나뿐이라, 일시정지는 다음 프레임을 예약하지 않기만 하면 된다.
- 버튼: 재생 중에는 "일시정지/재개 · 건너뛰기", 끝난 뒤에는 "다시 보기". 속도는 ×0.5 / ×1 / ×2 / ×4 중에서 고른다.
- 새 결과가 오거나 "다시 보기"를 누르면 `paused`를 `false`로 되돌린다. 속도는 유지한다.

### 6-4 비교 모드 + 두 지도 레이아웃

- 사이드바 알고리즘 패널에 "비교 모드" 토글을 둔다. 켜면 라디오 대신 알고리즘 두 개를 고른다 (기본 Dijkstra vs A\*, 같은 것은 못 고르게).
- 실행: `Promise.all`로 `searchGraph`를 두 번 부르고 결과를 `results: [a, b]`에 담는다. 하나라도 실패하면 오류 메시지만 보여준다 (기존 `searchIdRef`로 오래된 응답 버리기는 그대로).
- 지도 영역을 2열로 나누고 `MapView`를 두 개 놓는다. 각 지도 위에는 알고리즘 이름과 진행 상황(`방문 n / 전체`, 끝나면 `✅ 완료`)을 띄운다.
  - 출발/도착 핀, 영역 사각형, 클릭으로 지점 고르기는 두 지도 모두 같게 한다 (어느 쪽을 클릭해도 된다).
- 비교 모드를 끄면 지금의 단일 모드로 돌아간다. 모드를 바꾸면 결과는 지운다 (`clearResult()`).
- 구현 메모:
  - 지도 한 장(`MapView` + 이름표 + 경로 만들기)을 페이지 안의 `LabMap` 컴포넌트로 묶어 단일·비교 모드가 같이 쓴다. 결과도 `results` 배열 하나로 둔다 (단일 모드 = 1개).
  - 지도 폭이 절반이라 `LAB_LEVEL`(5)로는 영역 가로 2km가 다 들어오지 않아, 비교 모드는 한 단계 축소한 `LAB_COMPARE_LEVEL`(6)을 쓴다. 점(반지름 m 단위)도 그만큼 작게 보인다.
  - 모드를 바꾸면 지도 폭이 달라지므로 `key`를 바꿔 지도를 새로 만든다 (Kakao 지도는 컨테이너 크기가 바뀌면 `relayout()`이 필요한데, 새로 만들면 신경 쓰지 않아도 된다).
  - 두 지도는 같은 `shownCount`를 받고, 각 지도는 자기 방문 노드가 다 나오면 경로를 그린다. 재생은 방문 노드가 가장 많은 쪽이 끝날 때까지. → 6-5의 "공통 시계"와 "각자 끝나는 순간 경로 그리기"는 이미 이 방식으로 동작한다.

### 6-5 공통 시계 (`frame`)

> 6-4에서 `shownCount`를 두 지도가 같이 쓰는 방식으로 공통 재생·각자 경로 그리기·건너뛰기(긴 쪽 끝까지)는 이미 동작한다.
> 남은 것: 재생 진행을 **프레임 수**로 세어 "✅ 완료 · n프레임(약 n초)"을 보여주기. 속도를 바꿔도 두 지도의 끝난 시점 차이가 같은 단위로 보이게 한다.
>
> 구현: 상태를 `frame`으로 바꾸지 않고, 재생 길이를 방문 수에서 계산한다 (`playLength()`: `ceil(방문 수 / STEP)`프레임, 60fps로 나눠 초).
> 실제로 센 프레임은 속도(×0.5~×4)와 화면 주사율(120Hz 모니터는 `requestAnimationFrame`이 초당 120번)에 따라 달라지므로, ×1·60fps 기준 값으로 고정해 보여준다.
> 예: Dijkstra 1,200개 → 240프레임 (약 4.0초), A\* 580개 → 116프레임 (약 1.9초).

- `shownCount` 대신 `frame`(재생 시작 후 몇 프레임째인지) 하나만 상태로 둔다.
  - 각 지도: `dotCount = Math.min(frame * STEP, visited_order.length)`.
  - 재생 중 = 두 결과 중 하나라도 아직 덜 나왔다. 둘 다 끝나면 멈춘다.
  - 단일 모드도 같은 방식으로 바꾸면 재생 코드가 하나로 합쳐진다 (결과가 하나인 배열).
- 각 지도는 **자기 재생이 끝나는 순간** 경로를 그리고 "✅ 완료 · n프레임"을 표시한다. A\* 경로가 먼저 나타나고 Dijkstra는 계속 퍼지는 장면이 이 단계의 핵심이다.
- 건너뛰기 = `frame`을 둘 중 긴 쪽 끝까지, 다시 보기 = `frame`을 0으로. 6-3의 일시정지·속도는 `frame` 증가에만 적용하면 된다 (속도는 `frame`을 `speed`만큼 올리기).

### 6-6 비교 표

| 항목 | Dijkstra | A\* |
|---|---|---|
| 방문 노드 | 1,200개 | **580개** |
| 경로 거리 | 3,010m | 3,010m |
| 경로 노드 | 134개 | 134개 |
| 탐색 시간 | (서버 `elapsed_ms`) | |
| 재생 시간 | 4.0초 | **1.9초** |

(값은 5-6 API 확인 결과 기준 예시)

- 항목마다 더 작은 값을 굵게 표시한다. 경로 거리가 같으면 "같음"으로 표시해 두 알고리즘이 모두 최단 경로를 찾았음을 보여준다.
- 표 아래 요약 한 줄: "A\*는 Dijkstra 방문 노드의 48%만 탐색했습니다".
- 숫자는 서버 응답 그대로이므로 재생 중에도 보여준다 (5-4와 같음). 재생 시간만 끝난 뒤 채운다.
- 경로 없음(`cost = null`)인 쪽은 "경로 없음"으로 표시한다.

### 6-7 화면 확인

- 5-6과 같은 출발/도착(남서쪽 (35.1735, 126.9000) → 북동쪽 (35.1820, 126.9150))에서 Dijkstra vs A\*:
  - 두 지도가 같은 화면 범위로 시작하고 끝까지 유지되는지 (6-2).
  - A\*가 약 1.9초에 끝나 경로가 먼저 나타나고, Dijkstra는 약 4초까지 계속 퍼지는지.
  - 그라데이션으로 퍼진 방향이 보이는지, 경계 강조가 재생이 끝나면 사라지는지.
- 성능: 원 2,400개(1,200 × 2) + 프레임마다 경계 점 스타일 변경 시 재생과 지도 조작이 버벅이지 않는지.
  - 버벅이면 먼저 `handleMapClick`을 `useCallback`으로 고정한다. 지금은 렌더(재생 중 매 프레임)마다 새 함수라 `MapView`가 클릭 리스너와 커서를 매번 다시 등록한다.
- 일시정지 중 / 속도를 바꾼 뒤 / 건너뛰기 / 다시 보기가 두 지도에 똑같이 적용되는지.
- 예외 상황: 한쪽만 경로 없음, 출발 = 도착(두 지도 모두 점 1개), 영역 밖 400, 재생 중 지점 클릭·방향 바꾸기·초기화·모드 전환·탭 이동.

### 선택 (여유가 있을 때)

- **두 지도 이동 동기화**: 한쪽을 드래그·확대하면 다른 쪽도 따라간다. Kakao `center_changed`/`zoom_changed` 이벤트를 쓰고, 서로 계속 이벤트를 주고받지 않도록 "내가 옮긴 중"이면 무시하는 처리가 필요하다.
- **프런티어 표시**: 아직 확정되지 않은 후보 노드(큐)를 다른 색으로 보여준다. 백엔드가 프레임별 큐 상태를 보내야 해서 응답이 커진다. 가장 손이 많이 간다.
- **BFS/DFS 비교**: 6-4에서 알고리즘 네 개 중 아무 둘이나 고르게 열어 두면 따로 할 일은 없다.
