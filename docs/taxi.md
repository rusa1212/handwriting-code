# 택시 모드 작업 계획

> 목표: 경로 추천 탭에 **[택시 모드]** 를 추가한다. 출발지·목적지가 정해지면 바로 경로를 찾고, 경로마다 **예상 택시비**를 보여 준다.
> 택시비는 카카오가 주는 값(`summary.fare.taxi`)을 그대로 쓰지 않고 **요금 규칙을 직접 구현해 계산**한 뒤, 카카오 값과 비교해 검증한다. (`mapping.md` 8장: 직접 이해하는 것이 목표)

## 진행 현황

| 단계 | 내용 | 구분 | 상태 |
|---|---|---|---|

| 2 | 택시 요금 계산 모듈 (`be/taxi.py`): 기본·거리·시간 병산 요금 | 필수 | ✅ |

| 5 | 백엔드 API `POST /api/taxi` | 필수 | ✅ |

## 핵심 아이디어

택시 미터기는 **거리·시간 병산제**다. 빠르게 달릴 때는 거리로, 막혀서 느릴 때는 시간으로 요금이 오른다.

```text
택시비 = (기본요금 + 거리·시간 병산 요금) × 할증 배수     → 100원 단위
총 비용 = 택시비 + 통행료
```

- 카카오 응답의 `summary`에는 경로 전체의 거리·시간만 있다. 그런데 병산은 **구간마다 빠른지 느린지**에 따라 달라지므로 `sections[].roads[]`(도로 구간별 `distance`, `duration`, `traffic_speed`)를 써야 한다.
- 구간 속도가 기준(서울 15.72km/h) **이하**이면 그 구간은 시간 요금, **초과**이면 거리 요금으로 센다.
- 요금 계산은 경로 탐색과 무관한 **순수 함수**로 만든다: `taxi_fare(segments, depart_at, table) → FareBreakdown`. 그래야 터미널에서 숫자만 넣어 검증할 수 있다.

### 요금표 (초안, 서울 2023-02 개편 기준)

> ⚠ 구현 전에 서울시 공식 공지로 숫자를 다시 확인한다. 요금표는 코드 상수 한 곳(`TAXI_TABLES["seoul"]`)에만 둔다.

| 항목 | 값 |
|---|---|
| 기본요금 | 4,800원 (1.6km까지) |
| 거리요금 | 131m당 100원 |
| 시간요금 | 30초당 100원 (시속 15.72km 이하일 때) |
| 심야할증 | 22~23시, 02~04시 **20%** / 23~02시 **40%** |
| 시계외 할증 | 20% (서울 밖으로 나갈 때) |

## 1단계 ✅ 택시 계산 재료 꺼내기 (`map_api.py`, `schemas.py`)

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 1-1 | `Segment(distance, duration)` 스키마 + `_to_segments(sections)`: `roads[]`마다 거리(m)·시간(초) 추출 | ✅ 완료 |
| 1-2 | `get_routes()`에 `with_segments` 인자: 택시 모드에서만 구간 목록을 담는다 (자가용 응답 크기는 그대로) | ✅ 완료 |
| 1-3 | `Route`에 `kakao_taxi: int | None` 추가 (`summary.fare.taxi`, 검증·비교용) | ✅ 완료 |
| 1-4 | 확인: 구간 거리 합 = `summary.distance`, 구간 시간 합 ≈ `summary.duration` | ✅ 완료 |

- `roads[].duration`이 0인 구간(길이가 아주 짧은 구간)은 속도를 계산할 수 없으므로 거리 요금으로 센다.
- 응답을 파일로 저장해 두고 2~4단계에서 API를 다시 부르지 않고 쓴다. (키 사용량 절약, 결과 재현)
  - 처음엔 `be/data/sample_directions.json` 한 파일이었다. 받을 때마다 덮어써서 심야 샘플이 사라지는 문제가 있어 **`be/data/taxi_samples/directions_YYYYMMDD_HHMM.json`** 으로 바꿨다 (받은 시각마다 새 파일, 덮어쓰지 않음). 첫 샘플은 `directions_20261104_2315.json`(심야 40%)으로 옮겼다.
- 구현:
  - `get_routes()`를 `fetch_directions()`(API 호출, 원본 JSON) + `parse_routes(data, with_segments)`(파싱)로 나눴다. 저장한 응답을 API 없이 파싱하기 위해서다. `get_routes()`는 둘을 이어 부르므로 `/api/routes` 동작은 같다.
  - `Route.segments`는 `Field(exclude=True)`라 서버 안에서만 쓰고 응답 JSON에는 나가지 않는다. `kakao_taxi`는 응답에 나간다 (화면은 아직 쓰지 않음).
  - `python taxi_sample.py`: 샘플 4개를 저장(없을 때만, `--refresh`로 다시 받기)하고 구간 합을 `assert`로 확인한다.
- `python taxi_sample.py` 결과 (2026-11-04 응답):

| 샘플 | 구간 | 거리 (구간 합 차이) | 시간 (구간 합 차이) | 통행료 | 카카오 택시비 |
|---|---|---|---|---|---|
| 구미역→금오산 | 7 | 3,823m (0) | 590초 (0) | 0원 | 8,000원 |
| 전남대→광주송정역 | 11 | 14,259m (0) | 1,216초 (0) | 0원 | 17,400원 |
| 서울역→강남역 | 13 | 10,644m (0) | 1,421초 (0) | 0원 | 17,700원 |
| 서울역→인천공항 | 32 | 59,133m (0) | 2,990초 (−22) | 3,200원 | 69,200원 |

- 알게 된 것:
  - 거리는 구간 합이 정확히 같다. 시간은 긴 경로에서 22초(0.7%) 차이가 났다. 카카오가 구간 시간을 따로 반올림하는 것으로 보인다 → 요금 계산은 구간 값을 쓰므로 영향 없음.
  - **`roads[]`는 생각보다 거칠다** (경로 하나에 7~32개). 구간 안의 짧은 정체는 평균 속도에 묻힌다. 느린 구간(15.72km/h 이하)은 샘플마다 1~4개, 시간으로 25~210초뿐이다 → 시간 요금 비중이 작게 나올 가능성이 있다. 4단계에서 카카오 값과 비교해 확인한다.
  - 네 샘플 모두 `alternatives=true`인데 **경로가 1개만** 왔다. 7-3(후보 경로 늘리기)이 꼭 필요하다.
  - 지역마다 요금표가 다르므로(구미·광주는 서울과 다름) 4단계 비교는 서울 샘플 2개를 기준으로 본다.

## 2단계 ✅ 요금 계산 모듈 (`be/taxi.py`)

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 2-1 | `FareTable`(NamedTuple) + `TAXI_TABLES = {"seoul": ...}` 상수 | ✅ 완료 |
| 2-2 | 구간 분류: `is_slow(seg, table)` → 시간 요금 / 거리 요금 | ✅ 완료 |
| 2-3 | 병산 미터기: 기본거리를 먼저 소진한 뒤 거리·시간 단위마다 100원씩 올린다 | ✅ 완료 |
| 2-4 | `FareBreakdown(base, distance_fare, time_fare, surcharge, total)`: 화면에 내역을 보여 주기 위해 합계만이 아니라 항목별로 돌려준다 | ✅ 완료 |

- 구현:
  - 기준 속도는 따로 적지 않고 `FareTable.slow_speed = distance_unit ÷ time_unit`으로 계산한다. 서울은 131m ÷ 30초 = 4.37m/s = **15.72km/h**. 이 속도에서 거리 요금과 시간 요금이 같은 빠르기로 오르기 때문에 기준이 이 값이다. 요금표만 바꾸면 기준 속도도 같이 바뀐다.
  - 속도가 기준과 **같으면 느린 것**(시간 요금)으로 본다.
  - `taxi_fare(segments, table)`: "남은 기본거리", "쌓인 거리", "쌓인 시간" 카운터 3개. 카운터는 구간이 바뀌어도 이어진다.
  - 느린 구간도 거리는 달렸으므로 기본거리를 깎는다. 구간 중간에 기본거리가 끝나면 남은 비율만큼의 시간만 시간 카운터에 쌓는다.
  - `surcharge`는 3단계 전까지 0. `total`의 100원 반올림은 맨 마지막에 한 번만 한다.
- `python taxi.py` 손 계산 예제 9개 통과 (`assert`): 기본거리 이내, 딱 1.6km, 2,910m(10번) / 2,909m(9번), 구간을 넘어 이어지는 카운터, 느린 구간 300초, 기본거리에 걸친 느린 구간, 기준 속도와 같은 구간, 시간 0인 구간.
- 저장한 샘플 미리보기 (할증 없음):

| 샘플 | 직접 계산 (기본 + 거리 + 시간) | 카카오 | 카카오 ÷ 1.4 |
|---|---|---|---|
| 구미역→금오산 | 6,400 (4,800 + 1,600 + 0) | 8,000 | 5,714 |
| 전남대→광주송정역 | 14,400 (4,800 + 9,600 + 0) | 17,400 | 12,429 |
| 서울역→강남역 | 11,600 (4,800 + 6,700 + 100) | 17,700 | 12,643 |
| 서울역→인천공항 | 48,700 (4,800 + 43,900 + 0) | 69,200 | 49,429 |

- 알게 된 것:
  - 처음엔 모든 샘플이 카카오보다 17~35% 낮았다. 서울역→강남역은 "거리 요금 + 전체 시간을 모두 시간 요금"으로 쳐도(상한 16,400원) 카카오 값에 못 미친다 → 요금 계산 방식이 아니라 다른 배수가 있다.
  - 샘플을 받은 시각이 **2026-11-04 23:15** = 서울 심야할증 40% 구간(23~02시)이다. **카카오 `fare.taxi`는 요청 시각의 심야할증을 넣은 값**으로 보인다. 서울 두 샘플은 카카오 ÷ 1.4와 700~1,000원 차이다.
  - 남은 700~1,000원(시간 요금 7~10번 = 210~300초)은 1단계에서 걱정한 대로 **구간이 거칠어서 신호 대기 같은 느린 시간이 평균 속도에 묻힌 것**으로 보인다.
  - 서울역→인천공항은 시계외 할증까지 넣으면(× 1.6 이상) 거리 요금만으로도 카카오보다 커진다 → 카카오는 시계외 할증을 넣지 않는 것 같다.
  - 구미·광주는 지역 요금표가 달라서 비교 대상이 아니다.
  - → 3단계에서 심야할증을 구현한 뒤, 4단계에서 **낮 시간에 샘플을 다시 받아** 할증 없는 카카오 값과 비교한다. 저장 파일에 받은 시각도 함께 남기도록 바꾼다 (지금은 파일 수정 시각으로만 알 수 있다).

- **미터기 흉내 내기:** 실제 미터기처럼 "남은 131m", "남은 30초" 카운터를 두고 구간을 차례로 흘려보낸다. 단순히 `총거리 ÷ 131m`로 나누면 느린 구간이 섞인 경로에서 값이 달라진다.
- 기본거리(1.6km)를 다 쓰기 전에는 거리·시간 요금이 붙지 않는다고 가정한다. 실제 미터기는 기본거리 안에서도 느리게 달린 시간이 기본거리를 깎는데, 이 차이는 4단계 오차를 보고 반영할지 정한다.
- 금액은 정수(원)로만 다룬다. 할증 배수를 곱한 뒤 **100원 단위 반올림**은 맨 마지막에 한 번만 한다.

## 3단계 ✅ 할증 + 출발 시각

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 3-1 | `night_rate(depart_at, table)`: 출발 시각 → 0 / 0.2 / 0.4 | ✅ 완료 |
| 3-2 | 시계외 할증: `out_of_area_rate(origin, destination, table)` → 서울 안에서 밖으로 나가면 0.2 (사각형 bbox) | ✅ 완료 |
| 3-3 | 배수 합치기: 할증률을 **더한다** (심야 40% + 시계외 20% = 60%) | ✅ 완료 (규정 확인 필요) |

- 출발 시각 하나로 할증을 정한다. 운행 중 23시를 넘기는 경우(예: 22:50 출발, 30분 운행)는 처음엔 무시하고 문서에 한계로 적는다. (`conditionRoutingPlan.md`의 "출발 시각 하나로 상황 고정"과 같은 결정)
- `depart_at`은 기본값을 지금 시각으로 둔다. 서버 시간대가 아니라 **한국 시간**으로 판단한다.
- 구현:
  - 한국 시간은 `KST = timezone(timedelta(hours=9))` 고정 오프셋. `zoneinfo.ZoneInfo("Asia/Seoul")`은 Windows에서 `tzdata` 패키지가 없으면 `ZoneInfoNotFoundError`가 난다. 한국은 서머타임이 없어 고정 오프셋이면 충분하다.
  - 시간대 정보가 없는 `datetime`은 한국 시간으로 보고, 다른 시간대(UTC 등)는 한국 시간으로 바꿔 판단한다.
  - 심야 시간대는 요금표의 `night_rates`(`NightRate(시작 시, 끝 시, 할증률)`, 시작 포함·끝 미포함)에 둔다. 자정을 넘는 23~02시는 `(23, 24)`와 `(0, 2)` 둘로 나눠 적는다.
  - `taxi_fare(segments, table, night=, out_of_area=)`: 미터기 요금 × (1 + 할증률 합) → 100원 단위 반올림(50원 이상 올림. 파이썬 `round()`는 0.5를 짝수 쪽으로 보내서 쓰지 않는다). `surcharge = total − 미터기 요금`이라 내역의 합이 항상 `total`과 같다.
  - `FareBreakdown`에 적용한 `night_rate`, `out_of_area_rate`도 담는다 (화면에 "심야 40%"처럼 보여 주려고).
  - 시계외는 서울 안 → 밖일 때만 붙인다. 밖 → 서울은 붙이지 않는다.
  - `taxi_sample.py`: 저장 파일에 받은 시각 `fetched_at`을 함께 남긴다. 기존 응답은 다시 받지 않고 `{"fetched_at": "2026-11-04T23:15:58+09:00", "routes": {...}}`로 감쌌다 (심야 비교에 쓸 수 있는 귀한 샘플이라 보존).
- `python taxi.py` 할증 확인 (`assert`):
  - 심야 시간대 경계 12개 (21:59 → 0, 22:00 → 20%, 23:00 → 40%, 02:00 → 20%, 04:00 → 0, UTC 14:15 = KST 23:15 → 40% 등)
  - 기본요금만 나오는 거리: 심야 20% = **5,800원**, 40% = **6,700원** → 서울시가 발표한 심야 기본요금과 같다. 반올림 규칙이 맞다는 근거.
  - 시계외 20% = 5,800원, 심야 40% + 시계외 20% = 7,700원
  - 시계외 판단: 서울역→강남역 없음, 서울역→인천공항 20%, 인천공항→서울역 없음
- 저장한 샘플 미리보기 (받은 시각 23:15 → 심야 40%):

| 샘플 | 직접 계산 | 카카오 | 차이 |
|---|---|---|---|
| 서울역→강남역 | 16,200 | 17,700 | −1,500 (−8.5%) |
| 서울역→인천공항 (시계외 포함) | 77,900 | 69,200 | +8,700 (+12.6%) |
| 서울역→인천공항 (시계외 빼면) | 68,200 | 69,200 | −1,000 (**−1.4%**) |
| 구미역→금오산 (요금표 다름) | 9,000 | 8,000 | 참고용 |
| 전남대→광주송정역 (요금표 다름) | 20,200 | 17,400 | 참고용 |

- 알게 된 것:
  - 시계외를 빼면 인천공항은 −1.4%로 거의 맞는다 → **카카오 `fare.taxi`는 시계외 할증을 넣지 않는다**는 2단계 추측과 맞다. 우리 계산은 시계외를 그대로 두고, 4단계 비교 때만 빼고 비교한다 (실제 승객은 시계외를 낸다).
  - 서울역→강남역은 여전히 −8.5%. 거리·할증은 맞으므로 **시간 요금이 부족**한 것이다 (직접 100원 vs 차이 1,500원 ÷ 1.4 ≈ 시간 요금 11번 = 약 5분). 시내 경로일수록 신호 대기가 많아 구간이 거친 영향이 크다. 4단계에서 낮 샘플로 다시 보고 보정 방법을 정한다.

## 4단계 ⬜ 터미널 검증 (`python taxi.py`)

| 세그먼트 | 내용 | 상태 |
|---|---|---|
| 4-1 | 손 계산 예제: 기본거리 이내, 모두 빠른 구간, 모두 느린 구간, 섞인 구간, 심야 23시 | ⬜ |
| 4-2 | 저장한 카카오 응답 여러 개로 `직접 계산` vs `fare.taxi` 오차 표 출력 | ⬜ |
| 4-3 | 오차가 큰 경우 원인 정리 (구간 속도 판단, 기본거리 처리, 할증 포함 여부) | ⬜ |

- 낮 샘플: 22시 전에 `python taxi_sample.py --refresh` → `taxi_samples/`에 새 파일이 생기고 심야 샘플은 그대로 남는다. `python taxi.py`는 저장된 묶음을 **전부** 받은 시각의 할증으로 계산해 비교한다.
- 4-1은 `assert`로 고정해 나중에 코드를 고쳐도 깨지지 않는지 확인한다.
- 4-2 목표: 낮 시간 경로에서 **오차 ±5% 이내**. 카카오 `fare.taxi`가 할증·통행료를 포함하는지도 이 단계에서 확인해 문서에 적는다.

## 5단계 ✅ 백엔드 API (`main.py`)

| 엔드포인트 | 요청 | 응답 |
|---|---|---|
| `POST /api/taxi` | `{ origin, destination, depart_at? }` | `[{ id, distance, duration, toll, path, kakao_taxi, fare: { base, distance_fare, time_fare, surcharge, total, night_rate, out_of_area_rate } }]` |

- 내부적으로 `get_routes(..., with_segments=True)` → 경로마다 `taxi_fare()`. 구간 목록은 응답에 넣지 않는다 (화면에 필요 없고 크다).
- 카카오 오류는 기존과 같이 502로 돌려준다.
- 구현:
  - `schemas.py`: `TaxiRequest`(`depart_at: datetime | None`), `TaxiFare`(`FareBreakdown`과 같은 필드), `TaxiRoute(Route)` + `fare`.
  - `taxi.py`의 `taxi_routes(routes, origin, destination, depart_at, table)`: 이미 받은 경로에 요금을 붙이기만 한다 (API를 부르지 않는 순수 함수 → 저장 샘플로 검증 가능). 할증률은 출발 시각·출발지·목적지로 정하므로 경로마다 같다.
  - `main.py`의 `/api/taxi`는 `get_routes()` + `taxi_routes()`를 이어 부를 뿐이다.
  - `depart_at`: 생략하면 지금(한국 시간). `"2026-11-04T23:15"`처럼 시간대가 없으면 한국 시간, `Z`·`+09:00`이 붙으면 그 시간대를 한국 시간으로 바꿔 본다. 날짜로 읽을 수 없으면 422.
  - 요금표는 아직 서울 하나라 **다른 지역도 서울 요금으로 계산**한다 (8단계 지역별 요금표에서 해결).
- 확인 (`TestClient`, 저장 샘플로 `fetch_directions`를 바꿔 넣음):

| 요청 | 결과 |
|---|---|
| 서울역→강남역, `depart_at` `"2026-11-04T23:15"` (시간대 없음) | 200, 16,200원, 심야 40%, 내역 합 = 합계, `segments` 없음 |
| 같은 경로, `"2026-11-04T14:15:00Z"` (= KST 23:15) | 16,200원, 심야 40% |
| 같은 경로, `"2026-11-05T14:00:00+09:00"` (낮) | 11,600원, 할증 없음 |
| `depart_at` 생략 | 200 (지금 시각 기준) |
| 서울역→인천공항, 낮 | 58,400원, 시계외 20%, 통행료 3,200원 별도 |
| `depart_at` `"내일 저녁"` | 422 |
| 카카오 오류 | 502, `detail`에 카카오 오류 메시지 |

- 실제 API 호출 (2026-11-04 23시대): 서울역→강남역 16,200원 (카카오 18,000원). 거리는 같고 시간은 오히려 3초 줄었는데(1,421 → 1,418초) 카카오 값은 23:15 샘플(17,700원)보다 300원 올랐다. 우리는 구간 값만 쓰므로 같은 16,200원. 카카오가 요금을 어떻게 셈하는지(구간보다 촘촘한 내부 데이터, 다른 시간 요금 기준 등)는 응답만으로는 알 수 없다 → 4단계에서 낮 샘플을 여러 번 받아 차이가 일정한지 본다.

## 6단계 ⬜ 화면 (`RecommendPage.jsx` 외)

| 세그먼트 | 내용 | 상태 |

| 6-1 | 모드 토글 (자가용 / 택시): `mode` 상태, 모드를 바꾸면 결과 초기화 | ⬜ |

## 한계 (문서에 남겨 둘 것)

- 예상 요금이다. 실제 요금은 신호 대기, 기사 경로 선택, 실시간 교통에 따라 달라진다.
- 구간 속도는 카카오가 계산한 예상값이라 실제 정체와 다를 수 있다.
- 출발 시각 하나로 할증을 정하므로 운행 중 할증 시간대가 바뀌는 경우는 반영하지 않는다.
